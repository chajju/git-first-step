# /ship — 작업부터 PR까지 한 번에

사용자가 요청한 작업: **$ARGUMENTS**

이 스킬은 비개발 직군(PM, 디자이너)이 Git 흐름을 배우는 레포에서 쓰입니다.
아래 단계를 **순서대로** 진행하고, 각 단계를 시작할 때 무엇을 하는지 한 줄로 쉽게 설명해 주세요.
(예: "1단계: main 브랜치를 최신 상태로 맞출게요. 다른 사람이 올린 변경 사항을 먼저 받아오는 과정이에요.")

작업 내용(`$ARGUMENTS`)이 비어 있으면 아무것도 실행하지 말고 "어떤 작업을 해 드릴까요?"라고 먼저 물어보세요.

## 0단계: 사전 점검

1. `gh auth status` 로 GitHub CLI 로그인 상태를 확인합니다. 로그인되어 있지 않으면 멈추고 `! gh auth login` 을 실행하도록 안내합니다.
2. `git status --porcelain` 으로 커밋되지 않은 변경 사항이 있는지 확인합니다.
   - 변경 사항이 있으면 **멈추고** 사용자에게 어떻게 할지 물어봅니다:
     - 이번 작업에 포함하기 (새 브랜치로 그대로 가져감)
     - 잠시 치워두기 (`git stash`)
   - 사용자의 답 없이 변경 사항을 버리거나 덮어쓰지 않습니다.

## 1단계: main 최신화

```bash
git switch main
git pull --ff-only origin main
```

- pull이 실패하면(충돌, fast-forward 불가 등) 멈추고 상황을 쉽게 설명한 뒤 사용자에게 어떻게 할지 묻습니다.

## 2단계: 브랜치 만들기

작업 내용을 보고 `<타입>/<짧은-영문-설명>` 형식으로 브랜치 이름을 정합니다.

| 타입       | 언제 쓰나요                     |
| ---------- | ------------------------------- |
| `feat`     | 새로운 기능이나 화면 요소 추가  |
| `fix`      | 잘못된 동작이나 오타 수정       |
| `style`    | 색상, 여백, 폰트 등 디자인 변경 |
| `docs`     | README 등 문서 수정             |
| `refactor` | 동작은 같고 코드 구조만 정리    |
| `chore`    | 그 외 설정·잡무                 |

- 설명 부분은 영어 소문자와 하이픈(`-`)만 사용하고, 2~5단어 정도로 짧게 씁니다.
  예: `style/change-button-color`, `docs/update-readme-guide`, `fix/title-typo`
- `git branch --list <이름>` 과 `git ls-remote --heads origin <이름>` 으로 이미 있는 이름인지 확인하고, 있으면 뒤에 `-2` 등을 붙입니다.

```bash
git switch -c <브랜치명>
```

## 3단계: 작업하기

- 요청받은 작업을 수행합니다. 시작 전 관련 파일을 읽어 기존 스타일(들여쓰기, 문구 톤, 네이밍)을 따릅니다.
- 요청 범위를 넘는 수정은 하지 않습니다.
- 요청이 모호해서 결과가 크게 달라질 수 있으면 작업 전에 짧게 확인합니다.

## 4단계: 커밋하기

- `git status` 와 `git diff` 로 변경 내용을 확인합니다.
- 의미 있는 단위로 나눠 커밋합니다. 작은 작업이면 커밋 1개로 충분합니다.
- 파일은 `git add <파일경로>` 로 명시적으로 추가합니다. (`git add -A` / `git add .` 사용 금지 — 의도치 않은 파일이 섞이지 않게)
- 커밋 메시지 형식: `<타입>: <한국어로 무엇을 바꿨는지>`
  예: `style: 확인 버튼 색상을 파란색으로 변경`

## 5단계: 푸시하기

```bash
git push -u origin <브랜치명>
```

## 6단계: PR 만들기

`gh pr create --base main --head <브랜치명>` 으로 PR을 만듭니다.

- **제목**: 커밋 메시지와 같은 형식 (`<타입>: <한국어 요약>`)
- **본문** (HEREDOC으로 전달):

```markdown
## 작업 내용

- 무엇을, 왜 바꿨는지 1~3줄

## 변경 파일

- `파일명` — 바뀐 내용 한 줄 설명

## 확인 방법

- 리뷰어가 직접 확인할 수 있는 방법 (예: index.html을 열고 버튼 색상 확인)
```

## 7단계: 결과 보고

마지막에 아래 내용을 짧게 정리해서 알려줍니다.

- 만든 브랜치 이름
- 커밋 목록 (`git log --oneline main..HEAD`)
- PR 링크
- 다음 할 일 안내: "PR 링크에서 변경 내용을 확인하고, 리뷰 후 Merge 하면 main에 반영돼요."

## 절대 하지 않는 것

- main 브랜치에 직접 커밋하거나 푸시하기
- `git push --force`, `git reset --hard`, `git clean` 등 되돌리기 어려운 명령 실행
- 사용자 확인 없이 커밋되지 않은 변경 사항 버리기
- PR을 대신 Merge 하기
